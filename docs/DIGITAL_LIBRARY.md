# Digital library

## Security review — 23 November 2026

PDF uploads and stored PDF downloads now share bounded active-content checks; valid original bytes and hash validation are preserved. Opaque object streams/encrypted PDFs may require re-export. EPUB archive symlink entries are rejected, but EPUB XHTML/CSS/scripts/external resources are not comprehensively sanitized. No malware scanner or CDR service is installed. Keep publication restricted to authorized librarians with distribution rights, and complete the [production document safeguards](SECURITY_REVIEW.md#open-risks-and-required-follow-up) before real distribution.

## Setup

Use the project's supported PHP 8.5 and MySQL 8.4 environment. Enable PDO MySQL, Fileinfo, ZIP, XMLReader and GD. The library uses existing PHP extensions and adds no package dependency.

1. Back up the database and private files together. Stop application writes, run `php bin/database.php migrate`, then restart the app. Migrations 0061–0066 create the library tables. No books or account grants are seeded.
2. The default storage is `<project>/storage/library`, outside the `public` document root. Set `LIBRARY_STORAGE_DIR` to an absolute private directory when overriding it. Give only the application and cleanup worker access. Do not create a web-server alias to storage. Preserve this directory in backups with the corresponding database.
3. For uploads up to 20 MiB with a 3 MiB cover, configure PHP `upload_max_filesize=20M` and `post_max_size=25M`. Set Apache `LimitRequestBody 26214400` or Nginx `client_max_body_size 25m`. Restart PHP after configuration changes. Allow enough PHP memory for a bounded 20 MiB response and image decoding, typically `memory_limit=256M`.
4. Use the existing local server instructions in README. On Windows, use the supported PHP executable rather than an older XAMPP PHP. Public catalogue is `/digital-library`. Sign in with an existing administrator account and open `/dashboard/admin/library` to add resources. Teacher, school and parent sidebars link to the same catalogue, saved resources and history.
5. Run `php bin/library-cleanup.php` periodically using Windows Task Scheduler or Linux cron under the application's account. It retries up to 500 queued private file deletions. Upload and publication writes also attempt a smaller cleanup after commit. A failed deletion leaves a durable queue entry for retry. Monitor the private PHP/application error log and worker exit status.

## Publication and access

Administrators create private drafts with a PDF or EPUB material and optional JPEG/PNG cover. Metadata includes title, optional author/description/publication details, categories, subjects, education levels, licence, a private rights-evidence reference and optional rights expiry date. Unknown publication details can remain blank.

Publishing requires a current material, licence, evidence reference and explicit administrator confirmation that distribution is authorised. The checkbox starts unchecked on every edit. Every edit increments the revision, withdraws published resources and invalidates grants. Staff review and explicitly republish the revised resource. Licence expiry is inclusive of the chosen Africa/Lagos calendar date. Expired resources disappear from public details, search, covers and downloads.

Public catalogue metadata can describe Free, Restricted and Future paid resources. Free files download without registration. Restricted files require an active, email-verified account and an explicit administrator grant to that account for that resource revision. Pending schools can use the library. Grants expire within 365 days, can be revoked and are listed with cursor pagination. Granting or revoking one account does not change other accounts' grants. Publication changes revoke all grants. Future paid downloads remain disabled for everyone. Staff have a separately authorised, audited private preview for content review.

Materials use random storage keys without public paths. PHP checks publication, licence, account and grants again under database locks before reading and integrity-checking each file. Download responses use attachment disposition, no-store and nosniff headers. Covers also pass through PHP. HEAD performs checks without adding a download. Successful GET responses create an event, with a nullable user for visitors. Counts describe authorised responses generated by PHP, rather than proof that the client finished transferring or reading the book. No IP address is collected in the library download table.

Unpublish and archive retain files for staff review. Removal clears file references and catalogue metadata and queues the files for deletion. A minimal resource tombstone preserves foreign keys for statistics, saved records and download history. Saved records use a title captured when saved if the book becomes unavailable. History shows the title captured at download. Both show only “Resource removed” after removal. Unpublished revisions and private rights evidence remain hidden. Retained records and backup deletion must follow the deployment's documented retention policy.

## File validation and limits

- Materials support PDF and EPUB, up to 20 MiB. Validation checks authenticated upload provenance, actual size, extension, detected MIME and document structure. PDFs require consistent PDF header, cross-reference and trailer structure. EPUB archives require an OCF container and valid package/manifest/spine structure. ZIP entries are bounded and unsafe names, encryption, DTDs and archive expansion beyond limits are rejected. Archives are read in place and never extracted.
- Covers support JPEG/PNG up to 3 MiB, 5000 pixels per side and 20 million pixels overall. GD decodes and reencodes images, discarding original metadata and appended bytes.
- Structural validation cannot establish copyright ownership or guarantee a document has no harmful content for every reader. Staff should use the private preview and their established content/security review before confirming distribution and publishing. This release does not integrate a malware scanning service or perform full PDF/EPUB conformance certification.
- File reads verify size and SHA-256 and refuse unsafe links. Files stage before the metadata transaction. Replaced/removed keys enter a durable cleanup queue in the same transaction. Cleanup checks that no current resource references the key. If the database is unavailable during failed staging cleanup, a private orphan may require operational reconciliation after recovery. Never blindly remove files without checking current database references.

## Verification

Run `php tests/library-input.php`, `php tests/library-files.php` and `php tests/library-views.php` for metadata, structural file checks and view safety. Run `php tests/library.php` against an **empty disposable** loopback schema named `furoeducare_test_library_<suffix>` using `APP_ENV=development` and matching `DB_*` variables. It creates and seeds the schema, starts an isolated HTTP server and uses synthetic documents and users. Loopback socket access is required. It does not use the application's real database or publish fixture books there.

Run `php tests/database.php` with its separately named empty disposable schema to verify all migrations, upgrade, rollback and reapplication. Follow the local reset safeguards in `DATABASE.md`. Never point a reset or integration test at real account data.

After the main library suite, retain its disposable `DB_*` environment and run `php tests/library-roles.php` to check teacher and pending-school access, grant pagination and removal controls against that already migrated schema. The supplemental suite creates its own uniquely named fixture accounts. `tests/library-views.php` checks rendering without a database.

Manual checks:

1. Add a synthetic PDF draft and PNG cover as staff. Save without confirmation and attempt Publish. Expect validation. Add a valid licence/evidence reference, confirm distribution, save and Publish. Open catalogue, filters, details and cover as a signed-out visitor.
2. Download the free PDF without login and confirm the original bytes. Check the staff download count. Send HEAD to the download route and confirm the count is unchanged. Guess `/storage/<key>` and expect 404.
3. Sign in separately as a teacher, pending school and parent. Follow Digital Library, save a resource and download it. Confirm each account sees its own saved list and download history.
4. Edit the resource to Restricted, confirm and republish. Verify the guest and ungranted accounts cannot download. Grant one reader access with a future WAT expiry and reason. Confirm only that reader can download. Revoke access and verify immediate denial. Repeat with expiry and a second reader grant.
5. Change the file or rights details and verify publication is withdrawn and old grants stop working. Publish a Future paid listing and verify there is no enabled purchase/download path. Try an old staff form after another edit and expect a conflict.
6. Set an expired rights date on a synthetic resource and verify catalogue/details/cover/download exclusion. Unpublish, archive and remove resources, then check all old public URLs, history and the staff tombstone screen. Run the cleanup worker and verify queued unused files are gone.
7. At 360, 768 and 1440 pixel widths, inspect search, resource cards, metadata forms, grant controls and history. Check light/dark/system modes, keyboard focus, error messages, file re-selection after errors and pagination. This responsive/browser check remains a deployment review step unless explicitly recorded in implementation progress.
